# DATA.md — data sourcing, construction and test design

## 1. Where the data came from

No training data was supplied beyond the appendix tables, so **all data is synthetic and
generated by `src/data.py`**. No real tickets, scraped data, external datasets or
LLM/API calls at runtime were used. The scenario text was written by hand (with AI
assistance, listed in `AI.md`) and expanded by a seeded, deterministic generator.

Output: `data/synthetic_complaints.csv`, regenerated with `python -m src.data`.

| Column | Meaning |
|---|---|
| `id` | Row id (stable for a given seed) |
| `product_category` | One of the 7 values in Appendix A |
| `complaint_text` | The complaint (5–2000 characters) |
| `fault_category` | Label, one of the 12 values in Appendix B |
| `split` | `train`, `dev` or `test` (assigned per scenario, see section 4) |
| `scenario_id` | Opaque id of the underlying scenario. **Analysis and split validation only; never a model feature.** |
| `kind` | Scenario type: `plain`, `indirect`, `ambiguous`, `code`, `overlap`, `multilingual` |

The CSV deliberately has **no `escalate`, `confidence` or `reason` column** and no
`product_age_days`. Escalation (C1, C2), the age rule (C3) and confidence rules (C5, C6)
are deterministic rule-engine work, not something the dataset teaches the model.

## 2. How it was made

**Scenarios.** The unit of data is a *scenario*: one underlying situation (for example
"washer fills but the drum never turns") with 2–4 genuinely different paraphrases
(casual, formal, indirect, symptom-by-consequence). There are about 12–15 scenarios per
label, roughly 153 in total (see the summary printed by `python -m src.data`).

**Product awareness.** Every scenario lists the products it is valid for, so the data has
no impossible pairs (no fridge with a spinning-drum fault). Validity by label:
`not_heating` applies to washer, dishwasher, oven/cooktop, water heater, microwave and AC
(heat mode); `not_cooling` to fridge and AC only; `drainage_or_blockage` to washer,
dishwasher, fridge (defrost drain) and AC (condensate drain). Product nouns vary
("washer", "front loader", "geyser", "hob", "split AC", ...).

**Row generation.** Each row combines a scenario paraphrase with a product noun and then:
1. a wrapper: opener (Hi / Dear support / Urgent / ...), a label-neutral irrelevant
   detail ("we moved flats in March"), and a closer (thanks / signature / "pls fix asap");
   about 16% of rows become long narratives (4–8 filler sentences around the complaint);
2. noise: 35% clean, 40% mild (occasional typo, lowercase, dropped punctuation),
   25% heavy (1–4 typos from keyboard-neighbour/swap/drop/duplicate, text-speak like
   "wont/pls/u", ALL CAPS or lowercase, stripped punctuation).

About 140–150 rows are generated per label. Exact duplicates (after lowercasing and
stripping punctuation) are dropped across the whole dataset, so no text appears twice,
including across splits.

**Determinism.** Fixed seed (`SEED = 20261013`). Each scenario and split uses its own
string-seeded `random.Random`, so the output does not depend on `PYTHONHASHSEED` or on
the order other scenarios are generated. Re-running gives the same CSV.

## 3. Labelling decisions (hard cases)

- **C1 beats Appendix B wording.** Appendix B lists "trips the supply" under `no_power`,
  but rule C1 says a tripped supply is `electrical_or_control_board`. Tripped breaker /
  MCB / fuse complaints are labelled `electrical_or_control_board`. `no_power` examples
  avoid tripping language.
- **C5 ties.** Ambiguous scenarios (`kind=ambiguous`) are labelled with the *earlier* label
  in Appendix B. Examples: water leak vs drainage -> `water_leak`; heating vs motor ->
  `not_heating`; no power vs control panel -> `no_power`; a door seal that leaks ->
  `water_leak`; a door error shown on the display -> `door_seal_or_latch`.
- **C4 error codes.** A code on its own is `control_panel_or_display` (`kind=code`). A code
  plus a real symptom is labelled by the symptom (for example "drum never turns, shows
  E21" -> `motor_or_drive`).
- **C6 / `other`.** Thank-you notes (including "the leak was fixed, thanks", a hard
  negative), sales enquiries (including installation-price enquiries), spam, how-to
  questions, status enquiries, gibberish, and complaints with too little evidence
  ("it stopped working yesterday").
- **C1 vocabulary.** A few spark / smoke / burning-smell scenarios sit in
  `electrical_or_control_board` (and a few `overlap` ones mix them with another symptom)
  so the model learns the *category*. The model is **not** responsible for escalation.
- **C2.** One `not_heating` paraphrase mentions a gas smell with a burner that will not
  light. The label follows the rest of the text, as C2 says; escalation is the rule
  engine's job.
- **C3.** Installation scenarios are labelled by text content only (fit, levelling,
  connection, first use). The 30-day age condition is applied by the rule engine.
- **Languages.** `kind=multilingual` scenarios use Hinglish, Spanish and French words in
  Latin script, without accents.

## 4. Split strategy (leakage control)

Splits are assigned **per scenario, not per row**: every row of a scenario goes to the
same split. A held-out scenario is therefore a situation and a set of wordings the model
has never seen, not a re-skin of a training template.

- About 20% of each label's scenarios go to `test`, about 20% to `dev`, the rest to `train`.
- Each non-plain `kind` with two or more scenarios in a label is spread out: one to test,
  one to dev (if there are three or more), and one always kept in train. This is so that
  `code`, `overlap`, `ambiguous` and `indirect` behaviour can be evaluated, not only learned.
- `scenario_id` is opaque and is not used as a feature. It exists for split checks,
  `GroupKFold` and error analysis. The generator asserts that no scenario spans two splits.

## 5. How the data is used to test

1. **Tuning:** a train-only model, with the regularisation strength `C` chosen by dev
   Macro-F1.
2. **Final model:** fit on train+dev, then **scored once on `test`**. `test` is never used
   for tuning.
3. **Reported:** Macro-F1 over the 12 labels, per-class precision/recall/F1, accuracy by
   scenario `kind`, and mean confidence on correct vs wrong predictions (is confidence
   informative?). Command: `python -m src.classifier`.
